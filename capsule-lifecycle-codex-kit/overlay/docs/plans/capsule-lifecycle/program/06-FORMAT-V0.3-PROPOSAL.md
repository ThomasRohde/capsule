# Format v0.3 proposal

Status: concrete design input for M00/M01. The checked SQL and conformance
records produced by implementation become normative.

## Design goals

1. Separate immutable signed application release metadata from mutable capsule
   instance metadata.
2. Make lifecycle semantics explicit and signed.
3. Preserve exact allowlisting of `capsule_*` platform tables.
4. Keep ordinary domain rows mutable.
5. Allow rich host-rendered metadata without implying publisher trust.
6. Support signature-preserving fork and upgrade outputs.
7. Retain v0.2 as a separate supported profile rather than mutating its meaning.

## Singleton responsibilities

### `capsule_manifest`

Only immutable runtime/application release fields:

- format ID/version;
- runtime protocol;
- app ID/version;
- entry asset;
- requested permissions;
- data schema ID/version;
- minimum compatible host profile;
- application release creation time.

It does not contain capsule ID, title, instance summary or mutable timestamps.

### `capsule_application`

Signed display profile:

- application name and description;
- category;
- signed icon asset path;
- optional publisher-facing release notes slug.

### `capsule_instance`

Mutable user-owned profile:

- capsule ID and current revision ID;
- title and description;
- optional instance icon asset ID;
- document kind and tags;
- created and content-updated timestamps.

## Identity rules

- IDs are lowercase RFC 4122 hyphenated UUID text without a `urn:` prefix:
  `urn:uuid:xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`.
- `capsule_id` survives application upgrade and reconciliation.
- `revision_id` changes for fork, reconciliation and upgrade.
- exact and compact duplicates preserve both IDs.
- a fork creates a new `capsule_id` and `revision_id`.
- IDs are generated by the trusted host or authoring tool, never by browser
  application code during lifecycle operations.

## Time rules

All platform times are exact UTC RFC 3339 seconds. The host clock is operational
evidence, not trusted timestamp authority.

- application `released_at` is publisher asserted and signed;
- instance `created_at` is copied across upgrades;
- `content_updated_at` changes when the host creates a new revision;
- lineage event `occurred_at` records operation time.

## Instance asset rules

The first profile supports only PNG and WebP instance assets. The table stores
content hash, declared dimensions and bounded bytes. The host validates actual
dimensions before display. Instance assets are excluded from the publisher
signature but covered by structural integrity and output validation.

## Data contract rules

Every ordinary domain table participating in lifecycle operations is assigned
to exactly one signed dataset. A lifecycle operation requiring a complete
contract fails when a domain table is unclassified.

Dataset roles:

```text
seed
user-content
settings
history
derived
cache
sensitive
```

Policies are explicit for fork, compare, reconcile and upgrade. Dataset-table
rows declare primary-key columns and ignored/immutable columns. The host
cross-checks declarations against actual schema.

## Migration rules

Migrations form a directed graph over one `data_schema_id`. Each edge declares
one source and target integer version. The graph must be acyclic. Planning
requires exactly one accepted path; ambiguity fails closed.

Migration steps are data, signed in the application compartment and interpreted
by the trusted host. No SQL text or executable code is allowed in v0.3 migration
steps.

## Signed-app profile v0.3

Use a new profile and canonical-stream/signature context. Do not reuse v0.2
contexts.

The canonical stream includes signed tables and application/domain schema
required to define the application, while excluding mutable rows/tables listed
above. The verifier rejects unknown `capsule_*` objects.

The signature table remains outside the digest. A valid signature authenticates
an exact application digest but does not grant trust or capabilities.

## Compatibility

A host detects v0.2 and v0.3 by the exact `application_id`, `user_version`,
format version and runtime protocol tuple. Each profile has its own structural
contract and signed-compartment rules.

Do not add optional v0.3 platform tables to a v0.2 signed capsule. The current
v0.2 verifier correctly rejects unknown platform tables.
