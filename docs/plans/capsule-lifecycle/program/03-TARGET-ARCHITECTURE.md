# Target architecture

## 1. Architectural shape

The existing three-surface trust model remains:

```text
┌───────────────────────────────────────────────────────────────┐
│ Trusted Tauri shell                                           │
│ Overview · Cabinet · Copy/Fork · Compare · Upgrade · Security │
└───────────────────────────────┬───────────────────────────────┘
                                │ exact Tauri commands
┌───────────────────────────────▼───────────────────────────────┐
│ Product-independent Rust host                                 │
│                                                               │
│ capsule-core       inspect formats and bounded metadata        │
│ capsule-crypto     signed application compartment              │
│ capsule-workspace  lifecycle plans and create-new transforms   │
│ capsule-lifecycle  source pinning, writer lease, backup/restore│
│ capsule-runtime    named endpoint runtime after authorisation  │
└──────────────┬───────────────────────────┬────────────────────┘
               │ read-only pinned inputs   │ verified new output
       ┌───────▼────────┐           ┌──────▼─────────┐
       │ source capsules│           │ output capsule │
       └────────────────┘           └────────────────┘

┌───────────────────────────────────────────────────────────────┐
│ Raw Wry application renderer                                  │
│ Existing named endpoint bridge only; no lifecycle commands    │
└───────────────────────────────────────────────────────────────┘
```

## 2. New `capsule-workspace` crate

Add a product-independent workspace crate rather than broadening
`capsule-lifecycle`, whose current responsibility is source identity, writer
coordination, recovery and restore.

Suggested modules:

```text
native/crates/capsule-workspace/
  src/
    lib.rs
    error.rs
    limits.rs
    identity.rs
    profile.rs
    dataset.rs
    lineage.rs
    plan.rs
    publish.rs
    copy.rs
    compare.rs
    reconcile.rs
    migration.rs
    upgrade.rs
  tests/
```

### Responsibilities

- consume already-inspected/pinned capsule handles or open read-only sources
  under the same lifecycle policies;
- parse and validate v0.3 instance metadata, data contracts, lineage and
  migration declarations;
- construct immutable dry-run plans;
- compute deterministic plan digests;
- create only new output paths;
- validate outputs and publish atomically;
- produce bounded serialisable reports for CLI and Tauri;
- remain entirely product-independent.

### Non-responsibilities

- no Diagram Studio tables or semantics;
- no raw renderer integration;
- no trust-store persistence;
- no network or update discovery;
- no direct UI state;
- no arbitrary SQL supplied by callers;
- no in-place source mutation.

## 3. Application and instance compartments

### Signed application release

The signed compartment owns:

- format/runtime application fields;
- application ID and semantic version;
- application display metadata and signed icon pointer;
- entry asset and application assets;
- endpoint declarations and requested capabilities;
- checks, runbooks, prompts and docs;
- data schema identity/version;
- dataset lifecycle contract;
- migration graph and migration definitions;
- publisher identity.

The exact application digest remains the release identity used by local trust
policy.

### Mutable capsule instance

The instance compartment owns:

- capsule ID;
- revision ID;
- title and description;
- document kind and tags;
- optional safe instance icon/cover;
- creation and content-update timestamps;
- lineage events and parents;
- domain rows and ordinary change history.

Instance metadata is integrity-checked and bounded, but it is not publisher
authentication.

## 4. Host-local state

Keep host-local state outside capsules:

- trust and capability grants;
- revocations;
- backup inventory;
- recent/cabinet file paths and cached bounded cover metadata;
- compare-session handles;
- pending lifecycle operation state;
- release/update state.

A Cabinet cache is rebuildable and never canonical. It should be a separate
owner-protected store or clearly separated schema from trust decisions.

## 5. Lifecycle operation protocol

Every transforming operation has two phases.

### Plan

- pin and inspect all inputs;
- verify format, signature and contracts;
- derive compatibility;
- collect user choices;
- emit a bounded immutable JSON plan;
- bind exact source file identities, byte lengths, SHA-256 digests, capsule and
  revision IDs, application digests and data schema versions;
- compute `plan_digest`.

### Execute

- accept only a plan generated by the current host;
- rebind and reverify every source precondition;
- reject source WAL/shared-memory/rollback-journal sidecars, capture the pinned
  main database as raw bytes into a private create-new snapshot without opening
  SQLite against the source, and bind the exact snapshot SHA-256 used at plan;
- verify and read only that private snapshot during transformation, then
  recheck source identity, length, SHA-256 and sidecar absence after capture and
  immediately before publication so same-file and ABA writes cannot produce
  mixed state;
- create a private temporary output with create-new semantics;
- perform the operation transactionally on the output only;
- update instance/lineage as required;
- run integrity, foreign-key, signature, application-check and
  operation-specific validation;
- fsync file and containing directory where supported;
- atomically publish relative to a held, identity-bound, reparse-free parent
  directory handle to the user-selected leaf, which must not exist;
- return a verified result report.

A stale plan is rejected. It is never silently recomputed during execution.

## 6. Command surfaces

### Rust CLI

Extend or add product-independent commands with human and `--json` output:

```text
capsule profile <file>
capsule copy-plan <source> --mode duplicate|compact|fork|template
capsule copy <plan.json> <new-path>
capsule compare <left> <right> [--base <ancestor>] [--json]
capsule reconcile-plan <comparison> <selection>
capsule reconcile <plan.json> <new-path>
capsule upgrade-plan <working> <release>
capsule upgrade <plan.json> <new-path>
```

Exact names may adapt to the existing CLI, but JSON schemas and stable error
codes remain normative.

### Trusted Tauri shell

Register only narrowly scoped commands such as:

```text
get_capsule_overview
prepare_copy
execute_copy
start_comparison
get_comparison_page
prepare_reconcile
execute_reconcile
prepare_application_upgrade
execute_application_upgrade
```

Commands return host-defined structures. JavaScript never supplies SQL, table
names not already validated in a host session, or arbitrary output paths
outside a host picker result.

### Raw renderer

No new commands. The raw renderer remains limited to its current manifest,
permissions and named read/write endpoint protocol after launch authorisation.

## 7. UI state model

```text
no_file
  → inspecting
  → overview_locked | unsupported | rejected
  → trust_required | runnable
  → application_open

overview_locked
  → copy_workflow
  → compare_workflow
  → upgrade_workflow
  → security_review
```

Lifecycle inspection is independent of executable authorisation. A capsule may
be safely duplicated or compared while its embedded app remains locked, subject
to format and signature policy.

## 8. Compatibility

- v0.2 remains inspectable and runnable under existing policy.
- v0.2 supports duplicate and compact duplicate because neither changes logical
  identity.
- Signature-preserving fork and mutable profile require v0.3.
- A signed v0.2 capsule is not rewritten into v0.3 by the host.
- v0.2 to v0.3 occurs only by upgrading into a clean, verified v0.3 application
  release whose signed migration declaration supports the legacy source.
- Unsupported future formats remain bounded metadata-only where safe.

## 9. Publishing and recovery

Reuse proven create-new, protected temporary file and verification patterns from
signing and restore code. Lifecycle output inventory should be auditable but is
not automatically treated as a recovery backup unless explicitly registered.

No operation implicitly replaces the working capsule. The shell may offer
`Open new copy` after completion.
