# Canonical data and digest rules

Deterministic signatures, plans, comparisons and reconciliation preconditions
require explicit typed encodings. M00/M01 must freeze exact byte rules and publish
cross-implementation vectors before these digests become stable APIs.

## 1. Cryptographic primitive

Use SHA-256 where this programme says `digest`, unless an accepted versioned
profile specifies otherwise. Hex is lowercase, fixed 64 characters. Binary
signature-table storage may remain 32 bytes.

A digest proves equality/integrity under its canonical profile; it does not prove
publisher identity unless covered by a verified signature.

## 2. Canonical JSON

Plans/reports use a versioned canonical JSON profile:

- UTF-8 without BOM;
- JSON object keys sorted by Unicode code point after validation;
- no insignificant whitespace;
- arrays retain semantic order;
- integers use minimal decimal form;
- floating-point values are prohibited in lifecycle plan metadata unless a field
  explicitly defines its representation;
- strings use standard JSON escaping with no Unicode normalisation performed
  silently;
- timestamps are UTC RFC3339 seconds (`YYYY-MM-DDTHH:MM:SSZ`) unless a profile
  explicitly permits fractional seconds;
- the digest field itself is omitted from the bytes being digested.

Do not rely on language-default map iteration or serializer float behaviour.
Publish Python/Rust byte fixtures.

## 3. SQLite typed values

Row/value comparison must distinguish SQLite storage classes. Proposed binary
tagging:

```text
0x00                           NULL
0x01 + 8-byte big-endian i64   INTEGER
0x02 + 8-byte IEEE-754 bits    REAL
0x03 + u64 length + UTF-8      TEXT
0x04 + u64 length + bytes      BLOB
```

Rules:

- reject values that cannot be represented under the supported profile;
- define signed zero behaviour by preserving IEEE bits;
- reject non-finite REAL values rather than allowing serializer differences;
- compare/digest TEXT bytes as returned by SQLite under a validated UTF-8
  interface; do not normalise Unicode;
- never coerce `"1"`, integer `1` and real `1.0`;
- BLOB details default to length and SHA-256 in reports.

Confirm actual SQLite/rusqlite/Python behaviour in M00/M05 fixtures, especially
non-finite values and invalid text encodings.

## 4. Table and row identity

A data-contract table declares ordered primary-key columns. Row-key canonical
bytes are:

```text
profile marker
table-name length + UTF-8 table name
PK column count
for each PK column in declared order:
    column-name length + UTF-8
    canonical typed value
```

A row digest extends this with all compared columns in canonical schema/contract
order, excluding declared ignored columns. Immutable columns remain included
unless explicitly ignored for digest purposes.

Do not use SQL string concatenation, JSON conversion or collation-dependent text
sorting for digests.

## 5. Ordering

For streaming comparison:

1. obtain rows ordered by validated PK expressions generated by the host;
2. define deterministic ordering by SQLite storage class and value;
3. reject/handle unsupported collations explicitly;
4. do not allow capsule/UI-provided `ORDER BY`;
5. test composite keys and mixed storage classes.

If a table's declared key cannot support stable ordering under the accepted
profile, row-level compare/reconcile is unavailable.

## 6. Application digest

Signed-app v0.3 uses a distinct context from v0.2 and an exhaustive ordered table
list. Canonicalisation includes:

- SQLite object name/type/SQL under exact agreed rules;
- table rows in declared PK order;
- typed field values;
- signed application profile, assets, endpoints, checks, data contract,
  migrations and publisher profile.

It excludes instance/profile assets, lineage, grants, change history, signature
row and domain rows. Mutation vectors must prove every inclusion/exclusion.

## 7. File digest

Lifecycle plans bind SHA-256 of exact source file bytes in addition to filesystem
identity and logical identities. A compact duplicate has the same logical
revision but normally a different file digest.

Hashing must be bounded/cancellable according to file-size policy and rechecked at
execute. Optimisations may cache only when bound to strong file identity/size/time
and must fail closed on ambiguity.

## 8. Plan digest

A plan digest covers:

- profile/version;
- operation;
- all input file/logical/application/schema identities;
- output create-new decision;
- dataset/row/field choices;
- limits;
- migration path;
- expected output identity/digest;
- security-relevant confirmations.

It does not cover ephemeral UI text or the digest field itself. Execution refuses a
plan whose canonical bytes/digest do not match.

## 9. Compare report digest

A summary report digest covers compatibility, input identities, policies, limits,
truncation flags and included change summaries/details. Pagination tokens bind:

- report digest;
- dataset/table token;
- deterministic cursor;
- disclosure/sensitivity state;
- expiry/session.

A report produced under different limits is a different report.

## 10. Reconciliation preconditions

Each operation binds target row/value digests from the reviewed state. Execution
re-reads and compares before writing. A mismatch returns
`row_precondition_failed` or `stale_plan`; it never applies to the newer row.

## 11. Required vectors

Publish at least:

- canonical JSON primitives/strings/nesting;
- all SQLite storage classes;
- integer bounds and real edge cases;
- Unicode combining forms kept distinct;
- empty/large BLOB hashes;
- simple/composite/mixed-type PK rows;
- v0.2 and v0.3 application streams;
- lifecycle plan/report/reconcile/upgrade digests;
- one isolated mutation per signed/mutable compartment.
